## API Assumptions, Pagination & Sorting

The application is designed around a reusable, component-based architecture, with pagination, sorting, and data loading handled independently from the presentation layer.

The current API influences some of these design decisions because its feed endpoints return lists of story IDs rather than a conventional paginated collection of story objects.

### API pagination

A typical production API should expose pagination parameters as part of the API request rather than requiring the frontend to retrieve and manage large collections of data.

For example:

GET /stories?offset=0&limit=25

or, for cursor-based pagination:

GET /stories?cursor=abc123&limit=25

The backend should be responsible for determining which records belong to the requested page and returning only the required data.

A paginated response could also provide metadata such as:

json
{
"items": [],
"total": 250,
"nextCursor": "abc123"
}

This keeps pagination concerns within the API and prevents the frontend from having to retrieve and store unnecessary records.

### API sorting

Sorting should similarly be handled by the backend when the API supports it.

A request could specify both the field and direction:

GET /stories?offset=0&limit=25&sort=score&direction=desc

or with cursor-based pagination:

GET /stories?cursor=abc123&limit=25&sort=score&direction=desc

The backend can then apply the requested sorting before returning the page of results.

This is preferable to downloading a large dataset and sorting it in the browser because the API can sort the complete dataset rather than only the records currently loaded by the application.

### Current  API limitation

The API does not expose this type of general-purpose pagination and sorting interface for its story feeds.

The feed endpoints return story IDs, for example:

/topstories.json

The individual story data must then be retrieved separately:

/item/{id}.json

As a result, the application cannot simply request something such as:

/stories?offset=25&limit=25&sort=score&direction=desc

from the current API.

Pagination and sorting therefore have to be implemented at the application level.

### Current application approach

To avoid requesting every story immediately, the application divides the returned story IDs into chunks of 100.

For example:

250 story IDs

Chunk 1 → 1–100
Chunk 2 → 101–200
Chunk 3 → 201–250

The chunking is an application-level optimisation and is not pagination provided by the API.

Already-loaded story IDs are also tracked to prevent the same story from being requested repeatedly.

### Client-side sorting limitation

Sorting is currently performed by the application after story objects have been retrieved.

Conceptually:

API
↓
Story IDs
↓
Load story objects
↓
Client-side sorting
↓
Client-side pagination
↓
Reusable table component

This means sorting is limited to the stories that have already been loaded.

For example, if the application has retrieved 100 stories and the user sorts by score, only those 100 stories participate in the sort. Stories that have not yet been retrieved cannot be included in the result.

This is an important limitation compared with a backend-driven API, where the complete dataset could be sorted before the requested page is returned.

### Preferred API design

For a backend API designed specifically for this application, pagination and sorting should be first-class API features.

A reusable frontend data component could make requests such as:

GET /stories
?offset=0
&limit=25
&sort=score
&direction=desc

# My recommendation:
use cursor-based pagination:.

GET /stories
?cursor=abc123
&limit=25
&sort=score
&direction=desc


This would allow the frontend to remain focused on presentation, user interaction, and state management rather than implementing data retrieval and querying logic.

### Summary

The key assumption is that **pagination and sorting are ideally responsibilities of the backend/API layer when using large data sets**.

The frontend should request the data it needs and provide the appropriate query parameters, for example:

GET /stories?offset=0&limit=25&sort=score&direction=desc

When cursor-based pagination is more appropriate:

GET /stories?cursor=abc123&limit=25&sort=score&direction=desc

The current API integration cannot use this approach directly, so the application implements client-side pagination, chunked loading, and sorting as a practical workaround.

The reusable component architecture is designed so that these implementation details remain outside the presentation components and could be replaced by server-side pagination and sorting if a suitable backend API were introduced.
